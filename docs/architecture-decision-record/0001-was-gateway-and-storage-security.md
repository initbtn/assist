# 0001. WAS 단일 API 게이트웨이 및 백엔드 경유 스토리지 보안 아키텍처

- **상태**: 승인됨 (Accepted)
- **날짜**: 2026-10-28

## 맥락 (Context)

`assist` 시스템은 기술 동향 수집·분석, 벡터 검색(RAG), 텔레그램 봇 브리핑, 웹 뷰어 아카이브를 제공합니다.
데이터베이스(Supabase PostgreSQL + `pgvector`)와 오브젝트 스토리지(Cloudflare R2 / AWS S3)는 핵심 자산이며, 클라이언트 브라우저 환경은 역컴파일·네트워크 인터셉트·스크립트 주입 등 공격 표면에 항상 노출되어 있습니다.
따라서 클라이언트 환경에 데이터베이스나 스토리지의 직접 접근 권한을 부여하거나 자격증명을 노출하는 것은 심각한 보안 침해 위험을 초래합니다.

## 결정 (Decision)

### 1. WAS가 유일하게 공개된 API 게이트웨이
- 클라이언트 브라우저나 외부 클라이언트는 **오직 WAS(FastAPI API 게이트웨이)를 통해서만** 데이터와 상호작용합니다.
- 브라우저 환경에서 Supabase 클라이언트 SDK(`@supabase/supabase-js` 등)를 통해 데이터베이스에 직접 접근하는 것을 원천 금지합니다.
- 데이터베이스 접속 자격증명(`SUPABASE_DB_URL`, `service_role_key`, `anon_key` 등)은 서버 내부 환경변수(RAM/pass)로만 관리되며, 브라우저 정적 자산(HTML, JS, 번들) 및 클라이언트 반환 페이로드에 일절 노출되지 않습니다.
- 모든 데이터베이스 쿼리, 벡터 검색, 중복 검사는 WAS 백엔드 내부의 서비스 레이어(`app/ingest.py`, `app/rag.py` 등)에서 검증된 상태로만 실행됩니다.

### 2. 클라이언트 브라우저의 스토리지 직접 쓰기 금지
- 클라이언트 브라우저가 스토리지(Cloudflare R2 / AWS S3)에 직접 쓰기 작업을 수행하지 않습니다.
- S3/R2의 **Presigned PUT/POST URL을 클라이언트에 발급하여 브라우저가 스토리지로 직접 업로드하도록 허용하지 않습니다.**
- 모든 파일 업로드 및 아티클 저장은 클라이언트가 WAS API 엔드포인트로 전송(`multipart/form-data` 또는 JSON 페이로드)하고, WAS 게이트웨이가 인가·유효성 검증(크기, MIME 타입, 악성코드 등)을 마친 후 백엔드 내부에서 스토리지 공식 SDK(Boto3 / Cloudflare API)를 사용하여 저장합니다.
- 오브젝트 스토리지 자격증명(S3 Access Key, Secret Key, R2 Token)은 오직 WAS 백엔드 런타임에만 주입됩니다.

## 근거 및 트레이드오프 (Consequences & Trade-offs)

### 이점
- **공격 표면 최소화**: DB 및 스토리지의 엔드포인트와 인증키가 외부에 일체 노출되지 않으며, 인바운드 보안 게이트웨이(WAS) 뒤로 완벽히 격리됩니다.
- **중앙화된 검증 및 정책 통제**: 모든 I/O 요청이 WAS 비즈니스 로직을 통과하므로 인증, 권한 인가, 레이트 리밋, 페이로드 유효성 검사, 로깅 및 감사 추적이 한곳에서 일관되게 집행됩니다.
- **Zero-Trust 네트워크 부합**: GCP 인스턴스(`marine-edge-pc`)의 인바운드 8001 차단 및 Cloudflare 터널 기반의 단일 아웃바운드 파이프라인 아키텍처와 정확히 일치합니다.

### 트레이드오프
- 대용량 파일 업로드 시 WAS 서버의 네트워크 대역폭과 메모리를 경유하므로, 백엔드 리소스 부하가 발생할 수 있습니다. (현재 `assist`는 텍스트·마크다운·메타데이터 위주의 경량 브리핑 시스템이므로 부하 영향이 극히 미미함).
