# 0005. 엣지 환경의 배치 수집 격리(OS Cron) 및 Ansible 기반 선언적 인프라 구성

- **상태**: 승인됨 (Accepted)
- **날짜**: 2026-11-17

## 맥락 (Context)

`assist` 시스템은 오픈소스 기술 동향(GitHub Releases)을 정기적으로 수집하여 임베딩 및 지식 베이스를 갱신하고, 매일 듀얼 모델 기술 브리핑을 합성합니다.
현재 서비스가 구동되는 프로덕션 환경은 GCP e2-micro 인스턴스로, 메모리가 약 1GB로 제한된 전형적인 경량 엣지(Edge) VM입니다.

이러한 저사양 엣지 환경에서 정기 배치(Batch) 파이프라인(`scripts/daily-collect-and-brief.sh`)을 스케줄링하는 방식을 결정할 때 다음과 같은 기술적 문제와 트레이드오프가 존재했습니다:

1. **메모리 안정성 및 OOM 격리(Fault-isolation)**:
   - 오픈소스 릴리스 수집 및 문맥 보존 청킹(Contextual Chunking), 임베딩 연산은 일시적으로 CPU 및 메모리 스파이크를 유발합니다.
   - 이를 FastAPI 웹 애플리케이션 내부 비동기 루프(`asyncio.sleep` 또는 `APScheduler`)로 구동할 경우, 수집 작업 중 메모리 초과로 웹 서버 프로세스가 OOM(Out of Memory) 킬러에 의해 종료되어 실시간 대화 API 및 텔레그램 봇 전체가 마비되는 위험이 있습니다.
2. **배포 수명주기와 스케줄러 간의 결합도**:
   - 신규 기능 배포 시 컨테이너가 재시작되면 내부 타이머가 리셋되거나 실행 시간이 누락되는 문제가 발생합니다.
   - Uvicorn/Gunicorn 다중 워커 프로세스를 운영할 경우 각 워커마다 중복 수집이 실행되는 것을 방지하기 위해 분산 락(Redis Lock 등)과 같은 불필요한 과설계가 요구됩니다.
3. **인프라 재현성 및 형상 관리(IaC)**:
   - 수동으로 서버에 접속하여 `crontab -e`를 편집하는 방식은 설정 누락, 오타, 서버 재프로비저닝 시 재현 불가 문제를 야기합니다.

## 결정 (Decision)

### 1. 웹 애플리케이션 내부 타이머 배제 및 OS Cron 채택
- **스케줄링 주체 분리**: 일일 정기 수집 및 브리핑 합성은 웹 애플리케이션 내부에서 타이머를 돌리지 않고, 운영체제 커널의 `cron` 데몬을 통해 외부에서 독립적으로 트리거합니다.
- **프로세스 완전 격리**: 크론잡은 독립된 셸 세션에서 `curl`을 통해 진입점을 호출하거나 배치 스크립트를 실행하므로 웹 API 프로세스와의 결합도를 완전히 제거하고 OOM 리스크를 격리합니다.
- **독립 로깅**: 배치 실행 이력과 에러는 웹 애플리케이션 콘솔과 분리된 `/home/dominic/assist/daily-cron.log` 파일에 안전하게 누적 기록합니다.

### 2. Ansible Playbook을 통한 선언적 Cron 형상 관리
- **IaC(Code as Infrastructure) 표준화**:
  - `ansible/playbook-cron.yml`과 `ansible/hosts.ini`를 프로젝트에 포함하여, 크론잡 주기(`0 22 * * *`, UTC 기준 = KST 07:00), 실행 경로, 실행 유저(`dominic`)를 선언적으로 정의합니다.
  - `ansible.builtin.cron` 모듈을 사용하여 멱등성(Idempotency)을 보장하며, 복수 번 실행해도 단 1개의 크론 엔트리만 유지되도록 보장합니다.
- **원클릭 실행 래퍼**:
  - 개발자 로컬 머신에서 `scripts/run-ansible-cron.sh` 1회 실행으로 프로덕션 VM의 크론 설정을 검증 및 동기화할 수 있도록 지원합니다.

## 결과 및 영향 (Consequences)

### 긍정적 영향 (Positive)
- **OOM 전파 차단**: 1GB 저사양 엣지 VM에서도 웹 서버가 상시 안정성을 유지합니다.
- **배포 독립성**: 컨테이너 롤링 배포나 재시작 여부와 무관하게 매일 정해진 시각에 정확히 1회 수집 파이프라인이 구동됩니다.
- **인프라 재현성**: 서버 이전이나 신규 노드 추가 시 `run-ansible-cron.sh` 실행만으로 동일한 스케줄러 설정이 즉시 복원됩니다.

### 부정적 영향 및 완화책 (Negative & Mitigations)
- **외부 종속성**: 리눅스 crontab 데몬이 실행 중이어야 함 (시스템 기본 데몬으로 사실상 상시 활성 보장됨).
- **실행 타임존 주의**: 서버 시각(UTC)과 로컬 서비스 시각(KST)의 시차(9시간)를 명확히 인지해야 하므로, 플레이북 및 ADR에 `minute: 0, hour: 22 (UTC 22:00 = KST 07:00)` 주석과 명세를 고정합니다.
